Q2. How to run the gold solution for a train task: which ground_truth file or attribute holds it, its entry point, and the exact code string that, passed to world.execute, completes the task so world.evaluate() reports success. Save that code for task <task_id> to appworld_root/rdr_gold/<task_id>.py.
Answer: The gold lives in `data/tasks/<task_id>/ground_truth/compiled_solution.py`, exposed as `world.task.ground_truth.compiled_solution_code` (a string; the load needs `ground_truth_mode="full"`). The file is a module with imports and one function `solution(apis: ApiCollection, requester: Requester) -> None`. The function ends by calling `apis.supervisor.complete_task(...)` itself, so no separate completion call is needed. The entry point is therefore that function, and the code string that completes the task is the module source plus a call line. This is exactly what `appworld verify tasks` does (`verify.py`). Ground-truth files per task: `answer.json`, `api_calls.json`, `compiled_solution.py`, `evaluation.py`, `generator.py`, `metadata.json`, `private_data.json`, `public_data.json`, `required_apps.json`, `solution.py`, `test_data.json`. `GroundTruth` attributes: `answer, api_calls, compiled_solution_code, compiled_solution_code_body, compiled_solution_code_header, compiled_solution_module (method), evaluation_code, evaluation_code_body, evaluation_module (method), generator_code, metadata, private_data, public_data, required_apis, required_apps, solution_code, solution_code_body, solution_code_header, solution_module (method), statistics, task_id, test_data`. `api_calls` is a `list[dict]` of `{"method": str, "url": str, "data": dict}` (71 entries for the first train task, 8 for `T`). Saved to `appworld_root/rdr_gold/60d0b5b_1.py` (gitignored); running it in a fresh world gives `world.evaluate().success == True`. Over all 147 train and dev tasks this recipe passes 147 of 147 (own loop, since the CLI hides its tally, see Q9).
Code:
```python
code = world.task.ground_truth.compiled_solution_code + "\nsolution(apis, requester)\n"
world.execute(code)          # returns "Execution successful." on success
world.evaluate().success     # True
```

Q3. logs/api_calls.jsonl: field names and types of one line. Can each line be matched to app name, API name, arguments and response?
Answer: One line is `{"method": str, "url": str, "data": dict}` and nothing else (7733 of 7733 lines across the 147 gold runs have exactly these three keys). `method` is lowercase (`get`, `post`, `put`, `patch`, `delete`). `url` is the app-prefixed route with path parameters already substituted (shape `/<app>/<route>`, for example `/<app>/<collection>/<id>/<sub>`). `data` holds the query or body arguments; the `access_token` argument is kept inside `data` (present on 4424 of the 7733 gold lines). There is no response, no HTTP status, no timestamp and no API name. App name: first URL segment. API name: match `(method, url)` against the route templates from `appworld.requester._get_api_name_to_doc(app, include_private_apis=True)` (each entry has `path` with the `/<app>` prefix, and `method`), turning `{param}` into `[^/]+`. This mapped 7733 of 7733 gold lines to exactly one `(app, api_name)`, with 0 ambiguous. Arguments: `data` plus the substituted path parameters in `url`. Responses are NOT logged; they must be captured from the `world.execute` printed output or by calling through `world.apis` and recording the return value. The tracker adds the line before the HTTP call, so failed calls (4xx) are logged too and a line does not tell you whether the call succeeded. Excluded from the log: calls with `track=False` (for example the internal active-task check) and anything to the admin app. For `T`, the log after a gold run is equal, line by line, to `ground_truth.api_calls`. `AppWorld.parse_api_calls_log(experiment_name=..., task_id=...)` returns the parsed `list[dict]`.
Code:
```python
from appworld.requester import _get_api_name_to_doc
docs = _get_api_name_to_doc("venmo", include_private_apis=True)   # api_name -> {"path", "method", ...}
rx = re.compile("^" + re.sub(r"\{[^}]+\}", "[^/]+", doc["path"]) + "$")
```

Q4. dbs/<app>.jsonl: field names and types of one line. Does it give table, row id, and the row value before and after, or only after?
Answer: Each line is a JSON array of exactly three elements, `[statement: str, parameters: list, executemany: bool]` (all 14705 lines across the 147 gold runs have this shape; `parameters` is always a list; `executemany` is true on 43 of them). It is the SQLAlchemy cursor-execute event log (`DBChangesTracker`), i.e. a SQL write-ahead log, not a table dump (`format="changes"` in `_save_state`). Statement kinds seen: `INSERT INTO <table> (<cols>) VALUES (...)`, `UPDATE <table> SET <col>=?, ... WHERE <table>.id = ?`, `DELETE FROM <table> WHERE <table>.id = ?` (the filter is always a single `id = ?`). Allowed prefixes in the tracker are INSERT, UPDATE, DELETE, CREATE and DROP. Table: yes, in the statement text. Row id: for UPDATE and DELETE it is the last bind parameter; for INSERT it is NOT in the line at all, because the statement omits `id` and SQLite assigns it (the id is implied by insertion order into the table). Values: only AFTER values (the inserted row, or the new values in `SET`). There is no before image and no explicit old value. The file is cumulative since world creation and starts with the statements that build the task's initial state (for `T`: 18 in `supervisor.jsonl`, 9 in `venmo.jsonl`), so initial setup statements must be skipped by counting. Lines within one app file are in execution order; there is no global order across app files. Full per-table row state (including ids and before values) needs either a snapshot between calls or replaying statements onto the base DB; the live SQLite handle gives it directly (Q11).

Q5. Are api_calls.jsonl and dbs/*.jsonl rewritten after every world.execute call? (Execute two API calls in two separate world.execute calls and compare line counts after each.)
Answer: Yes. `AppWorld.execute` ends with `_save_state(output_db_home_path_on_disk)` (which deletes and rewrites the whole `dbs/` directory) followed by `save_logs()` (rewrites `logs/api_calls.jsonl` and `logs/environment_io.md`). Evidence on `T`, as (api_calls lines, venmo.jsonl lines, supervisor.jsonl lines, environment_io blocks): at init (0, 9, 18, 0); after execute 1 containing four read calls, including a login (4, 9, 18, 1); after execute 2 containing one `create_transaction` (5, 14, 18, 2); after execute 3 containing another one (6, 19, 18, 3). Each created transaction appended exactly 5 venmo lines (INSERT transactions, INSERT transactions_fts, INSERT notifications, two UPDATE users). Consequences: files are cumulative, so the lines belonging to execute k are `lines[prev_count:]`; attribution to a single API call needs one API call per `world.execute`. Calls made outside `execute` (through `world.apis`, Q11) are tracked in memory but reach the files only at the next `execute` (dbs and logs) or `world.save_logs()` (logs only); `world.save_state(id)` writes a copy of the changes files under `.../checkpoints/<id>/`.

Q6. Row-id stability: run the gold code; then run it again with one extra insert (for example a Venmo payment) before it. Do rows the gold code creates get different ids? If yes, Plan 2 must match created rows by content, not id.
Answer: Yes, ids shift, so Plan 2 must match created rows by content. Task `T`, app `venmo`. Run A (gold only): the new `transactions` row gets id N+1 and the new `notifications` row gets id M+1 (N and M are the table sizes before). Run B1 (a topped-up extra `create_transaction` through the API first, then gold): the gold-created transaction gets N+2 and its notification M+2, shifted by +1 in the same tables. The content of the gold-created `transactions` row is identical across A and B1 in every column except `id` (including `created_at`, `updated_at` and `record_hash`). The gold-created `notifications` row is NOT identical: columns `data` (the payload embeds the transaction id) and `record_hash` differ. So references to ids inside other rows' fields also move, and content matching must normalise or ignore embedded ids. Run B2 (an extra payment request instead): the gold transaction keeps id N+1 (different table), the notification id still shifts +1 (shared notifications table). The extra insert also has cross-app side effects (the balance top-up needed to afford it created rows in `venmo.bank_transfers`, `gmail` and `file_system`), so a "one extra insert" can touch several tables. With either extra insert, `world.evaluate().success` is False for the gold run, because the evaluator also checks for unexpected database changes. A silent trap: with `raise_on_failure=False` a failed API call (here an expired payment card, then insufficient balance for the gold payment) does not raise, so check state, not the "Execution successful." string.
Code:
```python
def dump(w):  # rowid-keyed rows for every table of every allowed app, except FTS shadow tables
    m = importlib.import_module(f"appworld.apps.{app}.models"); conn = m.SQLModel.db.connection
    cur = conn.execute(f"select rowid, * from {table} order by rowid")
```
Compare `dump` before and after, `created = set(after) - set(before)` per table. Dump BEFORE calling `world.evaluate()` (see Q11).

Q7. Volatile fields: run the gold code twice in fresh worlds. Which row fields differ between the two runs (timestamps, tokens)? This list becomes ignore_fields.
Answer: For `T`, two gold runs in fresh worlds produced identical end states in every column of every table of every app, byte-identical `dbs/*.jsonl` for the apps compared, and identical `api_calls.jsonl`. So the ignore_fields list measured for `T` is empty. Reason: the world clock is frozen (freezegun; `datetime.now()` in the shell did not move over a 2 second sleep and returns a fixed year in the past), access tokens are deterministic functions of (user, frozen time), and `record_hash` is a deterministic hash of row content. Caveat across tasks: running all 147 gold solutions in two separate processes gave identical `dbs/*.jsonl` and `api_calls.jsonl` for 142 tasks and differences for 5 (`3c13f5a_1`, `3c13f5a_3`, `df61dc5_1`, `df61dc5_2`, `df61dc5_3`), all in venmo: `record_hash`, `receiver_id` and `user_id` (so which person is chosen differs), `transaction_id`, `like_count`, and the `user_email` argument in the logged calls. The row counts were equal. Cause: dependence on `PYTHONHASHSEED`. Those five tasks produce identical output across processes with `PYTHONHASHSEED=0` and different output with `PYTHONHASHSEED=1`. I did not locate which line of gold or app code iterates a hash-ordered set. Decision for Plan 2: set `PYTHONHASHSEED=0` in the run script, and keep `record_hash` in `ignore_fields` anyway as a precaution, because it changes whenever any other column of the row changes.

Q8. Does replaying ground_truth.api_calls one call per world.execute reproduce a passing world.evaluate()? If yes, per-call write attribution comes from snapshots between calls.
Answer: Yes, with one required workaround. Replaying every entry of `ground_truth.api_calls` as its own `world.execute` reproduced a passing `world.evaluate()` on 147 of 147 train and dev tasks (7733 calls replayed in total), and the resulting `api_calls.jsonl` equals `ground_truth.api_calls` line for line on all of them. For `T`, the replayed end state (row by row, all tables) equals the gold-run end state. Access tokens inside the recorded `data` are valid on replay (deterministic). The workaround: the public `requester.patch(...)` fails with "No scheme supplied" because `Requester._patch` does not default `client`; it silently leaves the state unchanged (9 of 147 tasks failed until fixed). Passing `client=requester.client` for every method fixes it. Per-call write attribution therefore works as: after each replayed call, either diff a `dump` snapshot of the live DB (Q6 code) or take `lines[prev_count:]` of each `dbs/<app>.jsonl` (Q5).
Code:
```python
for c in ground_truth.api_calls:
    world.execute(f"_r = requester.{c['method']}({c['url']!r}, data={c['data']!r}, client=requester.client)")
```

Q10. Released GPT-4o outputs: how many train and dev runs have at least one failed requirement with label no_op_fail (collateral damage)? Path of the evaluation files used.
Answer: Not answerable as specified, and the label premise is inverted. (1) The released bundle `experiment-outputs-0.1.0.bundle` unpacks to 28 experiment directories under `appworld_root/experiments/outputs/`: `react`, `full_code_refl`, `plan_exec` and `ipfuncall` agents with `gpt4o` and `gpt4turbo` (and `llama3` and `deepseekcoder` for the first three), each in `_test_normal` and `_test_challenge` variants, plus an empty `default`. There is no train or dev experiment among them, and the project rules forbid opening test-split files, so I did not read any evaluation file (I listed directory names only). The count of train and dev GPT-4o runs with a failed requirement is therefore undetermined, and no evaluation path was used. (2) From `appworld/evaluator.py` (`TestTracker.prepare_test_data`): `no_op_fail` marks a requirement that FAILS when the agent does nothing, that is, a requirement that measures task progress. `no_op_pass` marks a requirement that PASSES when the agent does nothing, and is the family that detects collateral damage (a failing `no_op_pass` requirement means the agent broke something that was fine). So "failed requirement with label no_op_fail" counts runs that did not do the work, and collateral damage is "failed requirement with label `no_op_pass`". The same label is on every pass and failure in `world.evaluate().to_dict()` (`{"success", "difficulty", "num_tests", "passes": [{requirement, label}], "failures": [{requirement, trace, label}]}`), so the count is easy to compute on any run of our own. Options for the owner: generate our own GPT-4o (or other model) runs on train and dev through the same evaluator, or get explicit sign-off to read the test-split evaluation JSONs for the counting.

Q11. Is an in-process apis object reachable from Python outside world.execute (for example an attribute of world or the shell namespace)? Give the exact expression or "no".
Answer: Yes. `world.apis` is the same object as `world.shell.user_ns["apis"]` (checked with `is`), and `world.requester` is the same object as `world.shell.user_ns["requester"]`. Calls through `world.apis.<app>.<api>(**kwargs)` run in-process, are tracked (`world.requester.request_tracker.requests` grows) and modify the same databases, but nothing is written to disk until the next `world.execute` (dbs and logs) or `world.save_logs()` (logs only). The shell globals at start are `apis`, `requester`, the helpers `Date, DateTime, Time, Counter, Iterator, Requester, ApiCollection, deepcopy, defaultdict, itertools, json, math, pendulum, random, re, reduce, datetime, calendar` and weekday constants. Live database access without disk round trip: `importlib.import_module(f"appworld.apps.{app}.models").SQLModel.db.connection` is a raw `sqlite3` connection (used by `dump` in Q6), `...SQLModel.get_tracked_db_changes()` returns the in-memory change list (same 3-tuples as in the jsonl files), and `world.models` is the `ModelCollection`. Hazards: (a) `world.evaluate()` re-points these module-level DB handles, so a `dump` taken after `evaluate()` reads a different database (it differed from the pre-evaluate dump in the test), therefore always snapshot first and evaluate last; (b) creating a new `AppWorld` closes any previous one (`close_all`); for reference, the `AppWorld` public attribute list is: `add_login_shortcut, allow_datetime_change, apis, base_output_directory, close, close_all, environment_io, evaluate, execute, experiment_name, expose_internals, id_to_time_freezer, import_utils, init_defaults, initialize, load_state, max_api_calls_per_interaction, max_interactions, models, models_from_db_home_path, models_to_db_home_path, munchify_response, null_patch_unsafe_execution, num_interactions, output_checkpoints_directory, output_db_home_path_in_memory, output_db_home_path_on_disk, output_directory, output_logs_directory, output_misc_directory, output_version_directory, parse_api_calls_log, parse_datetimes, parse_environment_io_log, raise_on_failure, raise_on_extra_parameters, raise_on_unsafe_syntax, random_seed, remote_apis_url, remote_docker, remote_environment_url, requester, safety_guard, save_logs, save_state, shell, show_api_response_schemas, task, task_completed, task_id, time_freezer, time_freezer_id, timeout_seconds`.
Expression: `world.apis` (and `world.requester`).

Answer: Decision: **value matching**. Etiq cannot run in the same process as AppWorld, and in a separate Etiq environment AppWorld failed to construct, so both modes returned empty graphs; the decision is environment-forced.
