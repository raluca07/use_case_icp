analysis. Every arm evaluated the same 42 instances: 10 clean executions, 16 unrepaired faulty executions and
16 repair-variant faulty executions. Every number is an instance count within an arm, not a count of fault
mechanisms.

## What “logs” means in these arms

In this experiment, **log** means the `COMPLETE INTERLEAVED ACTION LOG` generated by `_action_log` in
[`src/rdr/v2_packager.py`](../src/rdr/v2_packager.py). It is not a generic operating-system log, model transcript,
Python debugger trace or database transaction log.

For every captured top-level AppWorld API call, the log contains two consecutive entries:

```text
[event index] app.api({sanitized arguments})
[event index] -> observed response
```

The entries are presented in execution order. The response is the response observed by the workflow, so a
runtime fault that changes what the workflow receives is represented in the log. Sanitization recursively removes
only credential-bearing fields named `access_token`, `refresh_token`, `password`, `api_key`, `otp` or `secret`.
Task-relevant values such as amounts, record identifiers, email addresses, descriptions and response bodies remain
unless they occur inside one of those removed credential fields.

The action log does **not** contain:

- explicit graph edges;
- Python local variables or intermediate arithmetic values that never cross an API boundary;
- internal Python assignments, branches or loop iterations;
- the executed source code, unless the arm separately adds source;
- a complete initial database snapshot;
- every internal or nested API call that is not represented as a captured top-level workflow call.

The arms containing this complete action log are exactly **B, G, H, P, Q, R, S, T, U and V**.

Several other packages contain call-related information but do not contain the action log:

- **Indexed common** contains only event indices and API names.
- **I** contains call arguments but no responses.
- **`STATE_CALLS`** and **`STATE_CALLS_SOURCE`** contain only call names and order.
- Graph arms can contain call nodes, argument labels, response nodes or record effects, but that graph rendering is
  not classified as a log.
- **N and O** explore a graph interactively and do not receive the complete action log.

## Common package definitions

- **Standard common:** original task, agent final message and final values of records changed during execution. It
  contains no detailed call history. W uses this without the call index; most non-state arms use it together with
  the indexed call-name section.
- **Indexed common:** standard common plus the ordered event indices and API names. Arguments and responses appear
  only if the arm separately adds a log, input section or graph containing them.
- **State common:** original task, task-scoped pre-execution inputs, agent final message and the corresponding final
  task state.
- **Executed source:** the actual workflow source used for that execution, including an admitted source mutation.
- **AppWorld graph:** execution provenance built from API calls, records, source spans, arguments, responses and
  typed `reads`, `writes` and `feeds` relationships.
- **Etiq graph:** native coded-pipeline lineage captured by Etiq. It represents captured states and operations but
  does not necessarily contain every primitive scalar transformation.
- **Fake graph:** the real flat graph's nodes, labels and edge-type counts with topology deterministically rewired.
- **Registered origin:** the privately selected event or record used to centre particular diagnostic arms. It is
  package-construction information, not an answer revealed independently to every arm.

No package contains the earlier user report or private gold fault label.

## Arm definitions

### Baselines and flat AppWorld graphs

- **A — Indexed baseline:** indexed common only; no complete log, graph or source.
- **B — Log baseline:** A plus the complete interleaved action log.
- **C — Real flat graph:** A plus all flat AppWorld call and record nodes with real edges.
- **D — Neighbourhood:** a two-hop graph neighbourhood around the registered record, cut before the model call.
- **E — Random slice:** a deterministic graph slice matched to D's size and edge types.
- **F — Fake graph:** the full flat graph with real nodes and labels but rewired edges.
- **G — Log + real graph:** B plus C.
- **H — Log + fake graph:** B plus F.
- **I — Arguments only:** ordered sanitized API arguments without responses.
- **J — Argument ablation:** C with arguments removed from call-node labels.
- **K — Neighbourhood + origin:** D with the registered origin explicitly retained.
- **L — Random slice + origin:** a matched random slice retaining the registered origin.
- **M — Origin removed:** the full real flat graph with the registered origin removed.

K, L and M use private truth during package construction and are diagnostic controls.

### Interactive arms

- **N — Adaptive walk:** starts from the registered record and permits one-neighbourhood-at-a-time exploration,
  early stopping and at most six expansions.
- **O — Forced walk:** uses the same flat graph and starting point but requires the available expansion budget to
  be exhausted.

N and O are the only evidence-interactive arms. All other arms receive their complete package in one model turn.
The Codex CLI transport technically exposed its standard read-only tool surface, but ran in an empty temporary
working directory; the runner rejected any tool event and recorded zero tool use. Thus no arm acquired evidence
outside its supplied package.

### Source and nested AppWorld arms

- **P — Log + source:** complete action log and executed source; no graph.
- **Q — Log + source + real graph:** P plus the real flat AppWorld graph.
- **R — Log + source + fake graph:** P plus the rewired flat graph.
- **S — Collapsed nested graph:** log plus group-level function and loop nodes; internal members remain hidden.
- **T — Opened nested graph:** log plus internal function/loop members and edges.
- **U — Collapsed graph + source:** S plus executed source.
- **V — Opened graph + source:** T plus executed source.

### Endpoint-state arms

- **W — Final-state-only baseline:** original task, final message and final changed-record values. It has no call
  index, log, graph or source.
- **X — W + source:** W plus executed source.
- **Y — Initial/final state:** state common only; no calls, graph or source.
- **Z — Initial/final state + source:** Y plus executed source.
- **`STATE_CALLS` — State + call names:** Y plus API names and order, without arguments or responses.
- **`STATE_CALLS_SOURCE` — State + call names + source:** `STATE_CALLS` plus executed source.

### Etiq and cross-system arms

- **`ETIQ_CODE_LINEAGE`:** indexed common plus the native Etiq coded-pipeline lineage graph. No AppWorld graph,
  action log or source-text section.
- **`APPWORLD_ETIQ_COMPOSITE`:** indexed common plus joined AppWorld and Etiq layers connected through verified
  response-to-code and code-to-argument bridges. It has no separate action log or source section.
- **`STATE_APPWORLD_GRAPH`:** state common plus one full public nested AppWorld execution graph.
- **`STATE_ETIQ_GRAPH`:** the same state-common package as `STATE_APPWORLD_GRAPH`, with a native Etiq graph instead.

The composite passed structural validation, but its bridge qualification requires any complete cross-layer effect
path rather than specifically requiring the path through the current fault's root cause.

## Metric definitions

### Strict detection

Strict detection is correct only when the reviewer correctly answers both whether a harmful fault occurred at any
time and whether harmful state or artifacts remain at the end. It is therefore possible to detect a fault without
localizing or classifying it correctly.

### Clean correct

The number of the 10 clean executions for which the reviewer correctly returns no historical fault and no residual
harm. An incorrect positive answer is a false alarm.

### Unrepaired correct

Strict detection on the 16 faulty executions without a repair. All arms scored 16/16 on this subset.

### Repair-variant correct

Strict detection on the 16 faulty executions containing a repair. The historical fault still occurred, and some
executions retain irreversible downstream artifacts even after the primary record is restored.

### Class correct

Exact fault-class agreement on the 32 faulty executions. The classes are:

- **Action:** an incorrect API action or argument without a source mutation or abnormal runtime condition.
- **Source:** defective executed source with otherwise normal runtime behaviour.
- **Runtime:** abnormal response, ordering, timeout, filesystem result or dependency behaviour with unchanged source.
- **Mixed:** source and runtime faults coexist and each is independently harmful.
- **Interaction:** neither component is harmful alone; only their combination causes the failure.
- **Amplified:** at least one component is harmful alone and their combination makes the outcome worse.

### Exact root cause

The reviewer must return the complete gold set of causal source locations as literal `file:line` values and the
complete gold set of causal runtime/action event indices. Missing an item, adding an item or substituting a later
effect event makes the instance incorrect.

### Statement root cause

The supplementary metric maps source lines to the smallest enclosing Python AST statement before comparison. For
example, a call-start line and its faulty argument line match when both are within the same multiline call. Runtime
event indices remain exact, and extra or missing causal events still fail the metric.

Across all arms this changes complete root-cause localization from `321/1,024` (31.3%) to `335/1,024` (32.7%).
Among the 640 evaluations with a source component, exact source-line recovery is `128/640` (20.0%) and
statement-level source recovery is `166/640` (25.9%). A01 and I06 do not improve because their disagreements concern
runtime-event selection rather than line granularity.

### Artifact localization

- **Historically affected artifacts:** records or files harmed at any point during execution.
- **Restored artifacts:** historically harmed artifacts subsequently returned to the correct state.
- **Residual harmful artifacts:** harmful artifacts remaining at the end.

Artifact precision measures how many claimed artifacts are correct. Artifact recall measures how many gold
artifacts were recovered. These are separate from causal localization.
